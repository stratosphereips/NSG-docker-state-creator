## SFM7 e2e remediation (2026-10-22, same day — lab untouched)

Diagnosis: all three failures were ONE detector-side classification gap.
`sfm7_divergence.command_class` delegated wholly to
`mutate_filter.is_mutating`, whose token list is calibrated for DIFF
ATTRIBUTION (DESIGN A1/A2/A3) and contains no state-creating verbs —
`is_mutating("touch /tmp/x") is False` → class "readonly". So in the
fail and control arms only `rm -f` was required-class (`touch` was not
counted → `required_executed` 1 vs 2), and in the enforcement arm the
armed `DeclarationPolicy` saw `touch` as readonly → `requires()` False →
no refusal → the undeclared mutating command executed rc=0. The
suspicion recorded above that the `sfm7=` kwarg was not reaching the
call site was wrong: the e2e `defender` fixture binds
`scripted_defender.execute` directly (tests/e2e/conftest.py) and the
kwarg was reaching the executor; `run_controller.py` issues no commands.
The detector was wrong, not the test expectations — SFM7's required-class
contract is fail-closed, so lowering the expectation to 1 would have
baked the coverage hole in. The ocx record shape on vault was fine.

Fix (code-side, `sms/sfm7_divergence.py`): added
`SFM7_MUTATING_TOKENS`, a fail-closed SUPPLEMENT (never a subtraction)
applied in `command_class()` after the shared filter — state-creating
verbs the shared filter classifies readonly (touch, mkdir, rmdir, tee,
dd, install, ln, cp, chown, chgrp, useradd, groupadd, crontab,
`sed … -i`, `>`/`>>` redirects to real paths) are raised to "mutating";
shared "mutating"/"unknown" verdicts and the shared READONLY_EXCEPTION
pass through unchanged. `mutate_filter.py` itself untouched — A1/A2/A3
attribution behavior for every other FM unchanged. Regression pins added
inside two existing unit tests (battery count unchanged, 30):
`test_command_class_mapping` (supplement verbs + readonly survivors) and
`test_execute_policy_refuses_undeclared_mutating` (armed policy refuses
an undeclared `touch` — the exact live failure).
